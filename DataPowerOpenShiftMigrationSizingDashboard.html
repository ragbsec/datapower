IBM DataPower Physical-to-OpenShift Migration Sizing Dashboard

Best-effort migration hypothesis for DataPower Gateway 11.0.2 (`11.0.0.2`). It uses observed physical-appliance utilization as a workload signal, not a one-to-one vCPU conversion. The output recommends a safe initial OpenShift topology for 12-vCPU / 64-GiB worker nodes and must be benchmark-validated before production commitment.

Migration limitation: Model 8441/8496 physical CPU threads are not equivalent to OpenShift vCPUs. CPU generation, virtualization, OpenShift routing/CNI, TLS/crypto behavior, policy mix, backend latency, worker contention, and node reservations differ. This calculator labels its output as an initial migration hypothesis; validate it with representative k6/Locust load testing before finalizing replicas, worker count, or VPC entitlement.

Production migration starting topology

  • Start with at least three dedicated 12-vCPU / 64-GiB worker nodes.
  • Place one DataPower replica on each worker using required pod anti-affinity and topology spread.
  • Start with equal CPU requests/limits and equal memory requests/limits to ensure the scheduler reserves the tested capacity.
  • Use 2 vCPU / 8 GiB per pod as the initial baseline; raise to 4 vCPU only after the test proves a 2-vCPU pod does not meet throughput/latency objectives.
  • Verify scheduling against `Allocatable`, not raw `Capacity`, on each worker node.

Validation guide

What this does and does not prove

The calculator uses the appliance CPU observation only as a workload indicator. It deliberately applies a 25–50% migration headroom because appliance threads and Kubernetes vCPUs cannot be equated. The recommended plan is an initial sizing hypothesis.

Benchmark gate before final sizing

  • Run k6 or Locust through the same OpenShift route/load-balancer, TLS/mTLS mode, DataPower policy flow, payload distribution, and backend latency used in production.
  • Measure achieved TPS; p50/p95/p99 latency; errors; DataPower CPU and throttling; pod memory; route/load-balancer behavior; and backend latency.
  • Keep sustained gateway CPU below your chosen operating threshold—typically 70–75%—and verify negligible throttling and zero OOM/restarts.
  • Test one-pod and one-worker failure scenarios, including rescheduling and recovery capacity.
  • Update the benchmark-adjusted factor only after the data supports it, then recalculate replica count and VPC entitlement.
